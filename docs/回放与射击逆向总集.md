# 第一篇 协议层：data.wotreplay 数据段权威参考

## 一、坐标系与全局约定

- 回放世界系 = BigWorld 系：水平 `(x, z)`，`y` = 接地高度（米）。车体前向
  `forwardWorld = (sin(hullYaw), cos(hullYaw))`【使用中】。
- type=10 姿态符号：`pitch 正 = 车头下坡（nose-down）`（GB109 20 实体 corr=−1.00）、
  `roll 正 = 车体向左倾`（假设，样本缺纯横移）【使用中】。
- 服务器 hitscan 判定：method20/38/8/1/32 与 method29 开火同钟（+0~1 tick），
  命中在开火 tick 一次性判定【辅助：fire_tick 对齐键的理论基础】。
- eid→tank_id 精确映射 = type=5（eid→昵称，昵称 @payload[57]）× battle_results
  （account_id→tank_id）联表【使用中；俯仰极限锚定表的数据源】。

### 2.2 type=7 prop2 — 打包角（len=14，2B 载荷，变化驱动广播）【使用中】

```
u16 = (炮塔偏航 coarse10 << 6) | 炮管俯仰比例 frac6
偏航 = (u16>>6)/1024 × 2π − π        （相对车体，0.35°/级）
俯仰 = ele − frac/63 × (dep + ele)    （炮塔系，正=仰角，按车型极限锚定）
```

- **frac=63 ↔ 俯角极限（炮管最低）、frac=0 ↔ 仰角极限（最高）**（T110 1617
  受控实验极限钳位 + 实战常态贴 63 + 反向锚定消除对照系统偏差，三方一致；
  弹道绝对锚回归斜率 0.997 排除其他刻度）。
- **frac 恒定 ≠ 冻结**：快速偏航段 frac 钉极限是炮管物理贴极限的**实时如实上报**
  （第三人称预瞄点在近地面的正常操作常态）。prop2 为变化驱动广播，值不变即不重发
  （服务器按需重发不变值）。`pitch_frozen` 标记仅用于 prop2 整流断流 >2s
  （AoI 边界/补发簇）的陈旧提示。
- 主视角/队友/敌方**编码完全统一**；全套车辆（含作者）炮管俯仰的主来源。
- 车型极限（dep/ele）来自 battle_results × tank_cache
  （`TankResolver::pitch_limits_from_battle_results`）；无锚定时回退链见 §八。
- 注意：偏航**只能取高 10 位**——整 u16 解码会把 frac 变化混入偏航（±0.3° 假跳变）。

### 2.6 type=5 — 实体创建【使用中】

eid→昵称（昵称 @payload[57]，1B 长度前缀原始 UTF-8 串——全域非 ASCII 合法，
解码 SSOT 见 replay-core combat::nickname）；初始属性 blob 含 prop2 初值
（与进世界后首个 prop2 采样一致）。作者解析 = 文件名昵称匹配。

**尾部属性表**（>100B 车辆实体包；按 (属性 id u8)(定长值) 序列，值长随 id 定）【使用中】：

- **id 13 = 进世界血量 u16 LE**（含耐久加成装备；跨场探针 30+ 实体与 @51 首包一致；
  重广播包恒为开局值）→ `loadout::initial_hp_from_type5`；尾部锚 `0c 00 0d ?? ?? 0e`
  （id12=1B、id13=u16、id14=u16），值域 100..10000 防误配；
- **用途 = 血量链 seed**：受害者受击前无任何 method1 时，无锚点则首刀降幅不可推导
  （CLI 掉血表缺首行 + `dmg_unattributed` 误报）。已落地 `combat.rs collect_initial_hp()`
  前插 seed（时钟回退 1ms 避免同钟冲突去重）；type=7 prop3 首事件伤害同享此锚点。
  旧客户端无尾部表时血量回退 payload[51] u16（该偏移在重广播包为**当前**血量，
  首包才等于开局值；GB109 旧格式验证通过）；
- **尾部 3+3+9 loadout 块** = 9 字节配件选择串（byte=ID，103=校准弹/110=强化装甲，
  敌方再物化亦带）→ `collect_vehicle_equipment`【使用中】射击复现双方搭载注入；
- id 11 = 匿名乱码名（长度前缀串，长度随账号变化）；id 12/14 = 1B/2B；id 15 = 8B；id 16/17 = 1B。

### 3.3 method38 (0x26) — 命中结果反馈（仅作者射击）【使用中】

```
[0..4]  victimVehicleId u32（服务器权威目标）           【使用中】
[4..8]  resultFlags32 u32 = flags16 + headerHi16<<16   【使用中】
[8]     resultCount u8 + n×(componentToken+rawState)   【使用中】
[尾]    modifierCount u8 + n×modifierId u32            【使用中】
```

resultFlags 位图（WotbTools 全 16 位 PROVEN + 样本复现）：0x0001 直接炮弹击杀 /
0x0002 攻击时目标已死 / 0x0004 起火 / 0x0008 跳弹 / 0x0010 材料击穿 / 0x0020 未击穿 /
0x0040 间隙层穿 / 0x0080 间隙层未穿 / 0x0100 内部模块穿 / 0x0200 内部模块未被穿 /
0x0400 履带受损 / 0x0800 火炮受损 / 0x1000-0x8000 爆炸分支（正 DF 材料 / 零 DF 间隙 /
模块波及 / 模块损伤）。穿透族谓词 0x1110（对结算 penetrations 269/270，r≈0.9924）。
高 16 位 headerHi 保留 raw（多数 0x0002=录像者关联位，但 Maus 批量边界见 0x0012/0x0028，
禁当命中位解码）；同钟多条 = 批量传输需语义去重。
组件号 31=引擎 32=弹药架 33=油箱 34/35=右/左履带 36=火炮 **37=炮塔旋转机** 38=观察装置
39=车长 40=驾驶员 41=炮手 **42=UNKNOWN 禁猜** 43=装填手
（crit/destroyed 位图 bit = token − 31，与 WI 实测对齐）；rawState **1=受损或乘员受伤
2=critical/禁用族（"摧毁"过强）0=命中但无新持久负面（"无变化"过强）**；
modifierId 1=精准火力 2=钨芯弹（加性叠加可并存 [1,2]，非互斥）。

### 3.5 method0x07 — 弹种广播（args 5B）【使用中】

```
[a0 u8][shell_global_id u32 LE]
```

a0=0/1 = 弹药槽位（同钟成对同值 = 双槽同弹）；a0=18 = 异构子命令（非弹种，解析排除）。
发射时刻最新广播 = 该发实际弹种（与 type=32 segment 一致 30/30）——命中通知未转发时
（含全部脱靶弹）兜底 `shell_id`（`shell_from_broadcast` 标记）。
**作用域 = 作者 avatar 弹药状态**：他人弹不可得（他人弹种走 0x1b 兜底，见 §3.4）。

### 3.7 method36 (0x24) — 瞄准快照（args = [len u8][protobuf]）【辅助】

（WotbTools 全字段 PROVEN；根标量均 fixed64）

### 3.8 method0x0d / method0x23 — 装填状态【0x23 使用中 / 0x0d 未使用】

- 0x0d：args(9) = `[entity][code][f32 秒]`。code=0 = 当前装填阶段时长
  （T110E5 8.805 / Type5H 12.494 / Type2605 19.013 / XM551 14.675；GSOR 鼓内 2.5、
  整鼓 14.486）；**code=3 恒 = code0 − 0.1s**（疑似换弹种惩罚后时长，跨四车一致）；
  code=4/7 仅弹鼓车（段时长）。
- 0x23（=Avatar method35）：args(13) = `[entity][f32 装填配置时长][u32 恒 0][u8 恒 0]`。
  float1 = 当前生效完整装填配置时长（非倒计时；本地 5 场 8 实体 43 事件：distinct 值
  median=3、递减对 1/3；Type5H 12.494→10.679≈×0.855 肾上腺素→复原 12.494，在配置值间
  跳变）。非弹鼓车尾 3B 恒 0（WotbTools 250/250）。
  消费：作为「权威有效时长」注入整夹重装的刻度（playback 切面 `reload_effective`；
  相位 f3 只覆盖相位起点，不能给出整夹时长）。

装填相位的**主数据源不是 0x0d/0x23，而是 updateArena 的 subtype 15/16/17**（见 §3.10 的
`0x30 subtype 15/16/17` 行），被前端装填条消费。

## 四、Vehicle 方法流（envelope = 受击者；全局广播）

### 4.1 method8 (0x08) — 直击通知（showDamageFromShot wire 调用）【使用中】

```

尾部 4B = [b0][b1][b2][b3]

- **shooter / victim**【使用中】：他人路径的目标配对（±0.05s 窗）与伤害归属；
  victim 快照 = method8 处理时刻受击者运行状态（WI 对齐锚点语义）；

  （与 type=32 同域 86/86）。受害者死亡时 result 4→2 改写（@0x16A9271，作用于 result 字段；
  客户端消费链见第三篇 §2.3）；
- **cmpIndex**【使用中】：服务器指定受击部件 0=底盘/履带 1=车体 2=炮塔 3=炮管
  （离地高度分层实证 med 0.70/1.17/2.84m）→ `server_part_index`，弹着点部件约束；
- **hash6**【使用中】：游戏客户端 DecodeShotSegment 两点编码——服务器在命中判定
  时刻写入的出入点部件 AABB 量化坐标。公式、轴序校准与客户端消费链见**第三篇 §二**
  （权威定义）。用途：射击复现 3D 视图的出入点标注（前端 `frontend/src/scene/tankViewer.js`
  ◆ 解码，调试语义）+ P1→P2 判定射线基准（位置与弹向均取服务器编码值）；
- **尾部 4B**【未使用·封存】：
  - b3 = 该次交互造成伤害/摧毁标志（res=3 → 1 占 228/229；res=1/2 → 0 100%；
    跳弹致模块损伤 → 1）——可区分多交互事件中哪次造成损伤；
  - b0 = 服务器装甲片编号空间（每型号独立、跨部件共享、非空间局部片，更像
    功能分组/模块簇；五回放 385 事件；与 method38 受损模块可联表：
    10785 件 4 ↔ 右履带摧毁×6、GSOR 件 05 = 油箱+双履带+引擎）；

  `[count u8，0xFF→u24 LE][count × u16]`；属性路径元素 = 裸 `Read(2)` u16。
- **事件 u16 语义：已系统性证伪全部静态假说**（2026-10-05 第二轮，7 回放 +

# 第二篇 客户端架构：游戏如何处理回放数据

> 分析对象：Steam PC 版 wotblitz.exe（32 位 PE，2026-09-02 build；镜像基址 0x400000）
> + 游戏资源 `Data/`（DVPL 解码）。方法：RTTI（TypeDescriptor → COL → vtable）定位类与
> 虚表；断言/日志字符串中的 `类::方法` 限定名还原成员函数面；512 条
> `C:/ba/tc/work/t/client/Classes/...` 源码路径还原工程结构；objdump 定向反汇编；
> DVPL 配置解码。

## 一、总览：回放的本质是"网络包流重放"

Blitz 客户端是 BigWorld 网络层 + DAVA 渲染引擎的混合体（源码路径双命名空间印证：
`Classes/BW/*` 与 `Classes/Battle|Replay|Lobby/*`）。回放文件的数据段就是录像者客户端
当时收到的 **BaseApp 包流**（bundle 消息），回放播放不重新模拟任何游戏逻辑，而是把
录制包按录制时钟原样回灌进与实战完全相同的处理管线 [实证]：

```
回放文件(.wotbreplay)
  └─ ReplayFile::readBytes/readData            [实证] 包读取
  └─ ReplayPlayer::StartPlayback               [实证] 播放控制（速度：replayPlaybackSpeedChanged / replayTimeWarp）
      └─ ReplayMessageHandler                  [实证] 15 个 on* 回调（见 §3.1）
          ├─ onBasePlayerCreate / onCellPlayerCreate / onEntitiesReset / onEntityControl
          ├─ onEntityCreate / onEntityLeave / onRestoreClient / onSwitchBaseApp
          ├─ onEntityMethod  ──→ 按 (实体类, methodID) 分发，如 AvatarGameLogic::showTracer
          ├─ onEntityProperty / onNestedEntityProperty ──→ 按 (实体类, propertyID) 分发 set_*
          └─ spaceData / spaceGone
  └─ 与实战共享的下游：
      ├─ volatile(type=10) → 实体滤波器（WGVehicleFilter2，实现见 src/replay/filter.rs；
      │   客户端渲染链见第三篇 §五）→ 每帧 output()
      ├─ VehicleFilterSyncSystem / DetachedTurretFilterSyncSystem（DAVA ECS）写渲染 transform
      └─ 呈现系统（TracerManager / GunRecoilSystem / MinimapObjectsController / UI...）
```

**结论 [实证]**：回放里的每一种数据（volatile/属性/方法/竞技场状态）在游戏中都有唯一
的处理入口，且回放与实战走同一入口。因此"游戏如何处理回放数据" = "客户端如何处理
服务器数据"，本篇即按数据类别给出该映射。

> 分析对象：Steam PC 版 wotblitz.exe（32 位 PE，2026-09-02 build，image base 0x400000）。

## 一、弹道/示踪线：MovementStrategy 类簇 [实证]

### 1.1 类体系与 vtable

RTTI 定位到 6 个弹道运动策略类，同一接口（10 槽 vtable），槽 2（每帧推进）按弹种分实现：

| 类 | vtable | 槽[2]（每帧推进） | 槽[8] | 语义 |
|---|---|---|---|---|
| `ShellMovementStrategy` | 0x3721F14 | 0x1722E40 | 0x6AFF60 | 普通炮弹 |
| `GuidedMovementStrategy` | 0x3721F40 | 0x17228C0 | 0x8A59A0 | ATGM 制导（槽[4]也独有 0x171F820） |
| `TorpedoMovementStrategy` | 0x3721F6C | 0x1722E40 | 0x8A3530 | 鱼雷（特殊模式） |
| `LightningMovementStrategy` | 0x3721F98 | 0x1722A30 | 0x8A0B60 | 雷击（showLightning） |
| `RailgunMovementStrategy` | 0x3721FC4 | 0x1722B90 | 0x8570A0 | 电轨炮（特殊模式） |
| `TracerMovementStrategy` | 0x36BDFA0 | （槽 2..8 同一桩 0x2528D8D0） | — | 基类/公共实现 |

继承关系由构造函数的 vtable 写入序列实证：4 个构造函数都先写 Shell vtable
（0x17113AB→Lightning ctor @0x1711370、0x17117D0→Railgun ctor @0x1711790、
0x1712832→Torpedo ctor @0x17127F0、Guided ctor @0x17110B0），再写各自派生 vtable——
**Guided/Torpedo/Lightning/Railgun 均直接派生自 ShellMovementStrategy**。
基类构造 @0x1712E10，删除式析构显示对象大小 0x180 字节。

### 1.2 对象布局：640 点弹道折线缓冲 [实证]

基类构造（0x17129D0）初始化：

- `+0x00 = 0.15f`、`+0x08 = 4.0f`；`+0x0C = 4.0×0.5 = 2.0`、`+0x10 = 0.5`（0.5 = 常量 @0x36356E4）；
- `+0x18..0x20 = (1.0, 1.0, 1.0)`（三轴系数向量）；`+0x24 = 0.15f`；
- `+0x34` = 构造参数；`+0x38..0x40` = std::vector（begin/end/cap），
  **reserve(640) 元素 24 字节 = {pos vec3, vel vec3}**（0x170FB00，容量 640=0x280）——
  预计算弹道折线的容量上限；

派生类附加字段（各 ctor）：Shell `+0x58..0x60`；Lightning `+0x64=0, +0x68=1.0, +0x6C=−5.0, +0x70=+5.0`；
Railgun `+0x60=参数, +0x64=1.0, +0x68=0`。

### 1.3 数据流：method29 → ShowTracer → 策略 [实证]

```

### 1.4 折线上的可视推进与固定步长模拟 [实证]

- Shell 槽[2] @0x1722E40 = **沿折线推进**：`距离 = dt × 当前速度模`（`[ebp+8]×[esi+0x24]`），
  超过与下一折线点的距离即吸附到该点并取其速度模为新的速度（`[esi+0x24]`），
  折线耗尽后清空计数并置完成标志 `[esi+0x44]=0`——**示踪线 = 沿预计算折线的匀速可视化**；
- 时间累积器函数 @0x1718D40：`acc += dt`，`acc ≥ 0.03`（常量 @0x363A524）才步进——
  **弹道模拟固定 ~30Hz 步长**，附带 ±80 条 vec3 缓冲管理；
- 弹道积分数学 @0x1718850（被 0x1718D40 调用）：含 **Quake 快速平方根倒数
  （magic 0x5F3759DF + 一次牛顿迭代，常数 0.5@0x36356E4/1.5@0x36356E8）**、
  速度阻尼系数 0.35（@0x3638988）与 70.0（@0x3632A80，速度归一基准）、
  以及"目标点−当前点"的水平距离归一——阻力+指向目标的混合积分，
  直线弹与制导弹（ATGM 修正）共用此骨架；
- 无重力常量（游戏常量区无 −9.8/−9.81 f32；9.81@0x3645540 为配置解析区）。
  与项目实测一致（launchVelocity 方向与炮口→终点连线夹角 0.03~0.04°）：
  **客户端示踪线为直线推进 + 速度阻尼可视衰减，无可感重力弧线**；ATGM 由
  GuidedMovementStrategy 覆盖推进逻辑实现转弯（hitpoint 无关）；
- 表现参数插值常量：105/420（@0x3722544/48）与 5/20（@0x363C640/0x363CAC0），
  由 `[tracer+0x30]` 参数在两档间线性插值（示踪线长度/寿命档位，具体含义未定名）。

## 二、DecodeShotSegment 两点编码（命中位置权威定义）

### 2.1 完整公式（内层 @0x1334E30，逐指令核对）[实证]

输入 segment u64（method8 元素 8B：`[result b0][cmpIndex b1][hash6 = b2..b7]`）：

```
cmpIndex = b1                        （b1 ≥ 4 触发断言 "cmpIndexInt < 4" @0x36E7F10）
box     = partBlock[cmpIndex]        （min = block+0x00 3f，max = block+0x0C 3f，部件局部系）
P1 = min + (max−min) × (b2, b4, b3)/255     （轴序：x←b2，y←b4，z←b3 —— 交错！）
P2 = min + (max−min) × (b5, b7, b6)/255     （轴序：x←b5，y←b7，z←b6）
输出两个部件局部点（int→float 转换 @0x2529660，除以 255.0f @0x364B110）
```

- **6 个量化字节 = 两个点**（入点/出点语义），每个点 3 轴各 1 字节、在部件 AABB 内线性插值；
- 字节→轴映射为**交错序**（x,z,y），注意这作用于**游戏内存中的部件块轴序**
  （见 2.2 与 itemDefs JSON 轴序的补偿关系）；
- `out1 == out2` 时走单点分支（showDamageFromShot @0x16A9380 与 DecodeHitMarkSegment
  @0x13381EC 都先做 3 dword 相等比较）——单点 = 点射终止（未穿/跳弹），双点 = 贯穿段。

### 2.2 轴序：穷举校准 + 块存储序补偿 [实证+对照]

- **穷举校准**（8 发 × 48 种排列镜像，对真实弹着测距）确认 §2.1 轴序：hull 三发
  0.09~0.28m、炮塔 0.41m。b4/b7（前向轴）40% 压 0xff 等端点值 = 入点钉盒前界面的
  真实特征；游戏内存部件块为 **{右, 高, 前}** 存储序，交错映射即其忠实反映。
  客户端把 P1/P2 经部件矩阵变换后放置受击特效——协议以此替代下发精确几何；
- **与 itemDefs JSON 轴序的补偿关系**：项目探针 `hitpoint_probe.rs`（直序 x=b2,y=b3,z=b4）
  实测 J39 84 发反推点距射线 median 1.87 m（随机基线 17.3 m），按字面交错序重测劣化到
  15.4 m。两者自洽的解释：游戏内存部件块轴序为 {右, 高, 前}（DAVA/BW y-up 惯例），
  itemDefs JSON 轴序为 {右, 前, 高}——反汇编的字节交换恰好被块轴序差补偿：

  | 量化字节 | 游戏块内轴 | 游戏块轴序 | itemDefs JSON 轴 | 直序探针映射 |
  |---|---|---|---|---|
  | b2/b5 | x | 右 | [0] 右 | ✓ |
  | b3/b6 | z（块内第3） | 前 | [1] 前 | ✓（经块轴序换算） |
  | b4/b7 | y（块内第2） | 高 | [2] 高 | ✓（经块轴序换算） |

  即：**直序字节映射是正确的**；反汇编给出的"交错"是游戏块内 {右,高,前} 存储序的
  忠实反映。残余 1.87 m 偏差来自数据源近似（itemDefs bbox 轴对齐盒 ≠ 客户端真实部件
  AABB + 部件原点/座高近似），不再是解码问题。

### 2.3 showDamageFromShot 消费链（@0x16A9130）[实证]

```
args = (this, …, elements 指针 esi, …)
元素数 = (esi[1] − esi[0]) >> 3                    ；8 字节/元素
逐元素:
  result = elem.b0
  若车辆已毁/无血（vtable+4 对象 +0xBA 字节=0 或 +0xB8 word≤0）
      且 result == 4（跳弹）→ result 改写为 2     ；@0x16A9271 cmp esi,4; cmove esi,2
      【被重映射的是 result 字段，非 cmpIndex】
  bboxes[4] = 车辆模型对象(this+0x74) + {0xA8, 0xC0, 0xD8, 0xF0}   ；4 个连续 24B 部件块
  partMatrixes[4] = 0x779480 / 0x779950 / 0x77A0C0 / 0x779910 四个调用返回的模型节点矩阵
  DecodeShotSegment(elem u64, &out1, &out2, …, bboxes, matrices)   ；@0x1335363 调用
  out1/out2 经 3x4 矩阵（旋转+平移，@0x16A93A0 起的 SSE 块）变换——
  入点→出点方向决定受击特效/贴花的朝向
```

### 2.4 弹孔位置的终局结论 [实证合并]

- **客户端机械语义**：hash6 就是 DecodeShotSegment 解码的两个 AABB 量化点——method8
  元素 u64 原样传入解码器，无任何转换。解码出的点经部件矩阵变换后放置受击特效/贴花，
  **不是 raycast**：车辆弹孔 = 弹道线×模型求交，raycast 属环境弹孔/装甲高亮路径。
  全函数（0x16A9130）无角度解码常量、无 Bullet 射线调用，即客户端没有任何隐藏的
  精确位置数据；
- **游戏可见弹孔 = 弹道线 × 坦克模型求交**（玩家实测确认弹孔与弹道入射一致；
  `OnExplodeProjectile`（0x15F1700）无直接 Bullet 射线调用；按 result 分派的 4 类事件
  （0x456ADA4/B1F4/AE44/B22C）经 `HitExtraEffectEvent`/`ExtraEffectsManager`/
  `VehicleExtraEffectHandler`（RTTI 实证）消费，消费链为虚调用静态不可达）。模型：
  客户端用 showTracer 广播的弹道线（全客户端可见）与坦克模型求交得弹孔位置，segment
  字节用于特效种类/朝向；
- **协议层含义**：hash6 两点在部件盒内的横向位置即服务器编码的全部位置信息，与真实
  弹着间存在量化 + 盒源偏差（0.1~0.4m 级）——该偏差真实存在于游戏本体，非复现错误；
- **项目侧对应**：红色 ●（弹道射线 × 部件约束）= 真实命中的最佳估计；橙色 ◆
  （segment 解码点）= 与游戏客户端机械解码同位的可视化（**调试语义**），由前端
  `frontend/src/scene/tankViewer.js` 实现；
- 精确弹孔位置仅经 hitMarks 属性发给受击者本人客户端，回放中不可得（第一篇 §七）。

### 2.5 兄弟函数 DecodeHitMarkSegment（hitMarks 属性）[实证]

`SBWUtils::DecodeHitMarkSegment`（断言 "outHitMarkSegment < 4"/"Incorrect hitMarks segment"，
外层 @0x1337C40 内层同 0x1334E30）：

- 输入 = Vehicle 属性 `hitMarks` 的 HitMarkPlacementInfo protobuf 中的 segment u64
  （`[ecx+0]/[ecx+4]` 双字）+ 4 个部件盒指针（栈上构建 bboxes[4]）；

- 调用者 @0x133E750（0x1A8 字节工作区，0x17F09F0 取模型资源）→ 贴花放置
  （TankHitMarkComponent → DAVA DeferredDecal）；
- 意义：**`hitMarks` 属性与 method8 元素共用同一 segment 解码数学**——其核心字段
  segment 的解码即 §2.1 公式，其余 protobuf 字段为贴花样式/寿命等表现参数
  （该属性未被录制，见第一篇 §七）。

## 四、回放文件读取与播放链 [实证]

- **文件结构**：`.wotbreplay` = zip 或同名目录（`ReplayZipBridge`/`ReplayDirectoryBridge`，

  （索引构建 @0x13D95A0：16 字节索引项 {size,type,time,文件偏移} 存 ReplayFile+0x50 vector）；

## 五、坦克位置渲染链 [实证]

- **每帧驱动**：@0x13C6FC0 取回放主时钟 double t（与播放时钟同源！），对每个车辆实体
  依次 `getLastInput → markPending → input(回灌最新样本) → output(t, target)`——

  p1/p2 = f32（yaw/pitch 类），p3 = Vector3 位置，p5 = Vector3（速度类）；

- **旋转换算**：`VehicleTransformSystem::Process` @0x83F010：读三个**弧度角**，
  各乘 0.5（半角），绕 −Y/−X/−Z 轴（.data 0x4034060/6C/78 处轴向量的符号位翻转）构造
  3 个四元数，相乘归一化写 comp+0x34（x,y,z,w）——**车体朝向 = yaw/pitch/roll 欧拉

- **炮塔链**：WGVehicleFilterHelper 内部 @0x1440C70 对 **(yaw,pitch,t) 关键帧时间线**

# 第四篇 WI 对照与本项目射击复现

> 分析对象：wotinspector（replays.wotinspector.com / map.wotinspector.com /
> armor.wotinspector.com）。方法：抓取 WI 前端资源与公开 API 逐层分析
> （React bundle → battle.json → Map Inspector WASM → shotsimulate blob 解码 →
> armor 查看器活体取证），并与本项目 combat.rs 提取链逐字段对照。
> 原始产物存 `tmp_wi_js/`（未入库）。

## 一、总体架构

WI 的"3D 查看器"不是网页 JS 渲染，而是**整个 Emscripten WASM 原生应用**
（Map Inspector，C++ 编译，自带 WebGL 渲染器）：

```
replays.wotinspector.com/en/blitz/view/<hash>/      ← React 摘要页（射击表格/战绩）
   ├─ battleDetailsUrl  api.wotinspector.com/v2/battles/<arena_unique_id>/?platform=blitz
   │     → 服务器预解析 JSON：shots 表 + chat（§二）
   ├─ "Watch online" → iframe: map.wotinspector.com（WASM 自行下载完整 .wotbreplay
   │     解析包流、加载游戏数据包后本地渲染，§三）
   └─ shotsimulate    api.wotinspector.com/v2/ai/shotsimulate/（装甲查看器复现弹道，§四）
```

**网页 shots 表与 3D 查看器是两套数据流**：表格是服务器预解析统计 JSON；
3D 查看器拿到原始回放文件在浏览器内解析，可用参数 ⊇ 本项目 combat.rs 能提取的全部字段。

## 二、网页 shots 表（battle.json）字段清单

每发命中弹一条（脱靶无记录）：

| 字段 | 与本项目对照 |
|---|---|
| time / shooter / target | fire 时刻 + eid 配对（同源） |
| has_damage | method1 血量链归属 |
| shell_id | type=32 segment u24 / 项目 `shell_id`（已对齐） |
| turret_yaw / gun_pitch (rad) | prop2 @命中通知时刻（项目 `target_turret_yaw/gun_pitch`，已对齐） |
| **segment**（u64 十进制串） | **[result u8][layer u8][hash6 6B]**（§五） |
| distance | 流序 type10 欧氏距离，μ 级可复现 |
| nominal_pen / nominal_damage | item_defs 弹种表 |
| damage / hit_flags / crit_modules / destroyed_modules | method38 位图（已对齐） |
| is_premium_ammo / ammo_type | type=28 + 弹种表 |

**整表没有任何命中坐标字段**——WI 与本项目收到的是同一份无坐标协议。

## 三、3D 查看器（WASM）内部

wasm 字符串（13232 条唯一串）显示其内嵌：

- **BW 协议绑定**：与项目 type=10/prop2 同源的实体位置/姿态流解析；
- **自有 Arena 事件流**（protobuf）：发射/终点/爆炸/炮塔角/移动/血量变化；
- **完整装甲穿透模拟**：`piercingPower`（含距离衰减）、`getPiercingChance`、
  `armourPiercingFactor`、`use_armor_homogenization`、`ricochetAngle`、`isHEShell`；
- **碰撞模型与射线求交**：`hitTester/collisionModelClient`，模型路径
  `vehicles/{nation}/{tank}/collision_client/{gun}.model`（即游戏
  `3d/Tanks/CollisionMeshes` 同源几何，模块 id 决定炮塔/炮管变体）；
- **弹道行为设置**：`continue_trace_if_no_hit`、`use_hit_angle`、`chance_to_hit_by_projectile`。

## 四、shotsimulate：解析器向 armor 查看器传递的信息

模板（map-inspector.wasm 内明文）：

```
pkg={}&target.vehicle={}&target.chassis={}&target.turret={}&target.gun={}&
target.turret.yaw={}&target.gun.pitch={}&shooter.vehicle={}&shooter.chassis={}&
shooter.turret={}&shooter.gun={}&shooter.shell={}&segment={}&distance={}
```

返回 armor.wotinspector.com URL，其 `shot=` 参数为 base64url 的 **58 字节 shot blob**
（armor 端经 `--setting arg.shot <blob>` 注入）。逐字段可控变量探针测得的布局：

```
偏移    类型  字段
[0]     u8    =0x02（版本/魔数）
[1]     u8    =0x01（恒定）
[2..22) u32×5 shooter.{vehicle, chassis, turret, gun, shell}（模块/弹种 id）
[22..38) u32×4 target.{vehicle, chassis, turret, gun}
[38..42) f32  target.turret.yaw（度；= prop2 粗10位 × 0.3515625°，实测 126 步精确）
[42..46) f32  target.gun.pitch（度；prop2 frac6 按车型极限解码的连续值）
[46..54) u64  segment 原样（[result][layer][hash6]；服务端可能重编码，见 §五）
[54..58) f32  distance (m)
```

**没有传递**：命中坐标、发射点/弹速、目标世界位置与车体朝向、任何时间线。
armor 查看器收到 blob 后设置 `scene.shotSimulate{PlayerId,TargetId,TargetAngles,
Distance}`，调 `simulateShot` 对目标 `collision_client/{gun}.model` 射线求交。

**姿态取样语义**（原始回放逐发对照 21/21 验证）：blob 的姿态 = method8 直击通知
包在包流中出现时刻的**流序最后已知**受击者 prop2 快照（单遍流式解析器状态，非时钟序）：
距离 = 双方 type10 欧氏距离（μ 级）、炮塔角 = prop2 粗10位（逐位）、炮管俯仰 = frac6
按扇区极限解码（与项目解码等值反号，WI 压角为正）。**hull 车体角完全不取样**——
armor 查看器中车体恒默认朝向。项目 combat.rs 已按流序落地同构快照
（`DirectHit8::victim_prop2` / `LaunchEntry::shooter_prop2`），炮塔角/俯仰/距离逐位复现。

**服务端重编码**：shotsimulate 返回的 segment 与 battle.json 原值不同
（实测 `01 02 41 5a ff 41 61 c2 → 00 02 41 5a ff 41 77 00`：result 与末字节对被改写）
——armor 端展示的是 WI 自己模拟管线的输出，非游戏弹着的原样重建。

## 五、WI 对 hash6 的消费方式与服务器判定一致性

### 5.1 WI armor 查看器的消费方式

- blob 姿态角（turret.yaw/gun.pitch，度）摆位目标模型；**判定射线 = 受击者炮管轴反向**
  （方位 = 180°−turret.yaw、俯仰 ≈ gun.pitch），横向锚定在炮耳轴附近；
- hash6 六字节对射线做**差分斜率微调**：`dir(炮塔系) = normalize(kx·Δb2, ky·Δb3, 1)`，
  kx=0.00258、ky=0.00135（活体差分实验三点拟合，V3/A 方位 23.57°/18.13° 逐位复现）。
  注意该公式丢弃前向轴 Δb4−b7 分量，只是 WI 的方向近似；
- **本质 = 检视视线**：弹道的横向偏移不在任何字段里，WI 用"来向 ≈ 炮管反向"假设
  展示准星处的装甲剖面与该处模拟弹结果——其弹着标记与游戏真实弹着之间的系统偏差
  协议层面不可消除；面板数据流：`armorTraced(ray, points, …)` →
  `ShotResult.computeShotResult` → 穿透率着色与预后（散布 = ShotDispersionRadius×0.01×distance，
  穿深按 `getEffectivePiercingPower(distance)` 距离衰减）；
- `retraceLastShot` / `resetCameraToLastShot` 为刷新重放入口——`arg.shot` 一次性消费 +
  trace 状态依赖启动时序，竞态失败即落回默认姿态（"刷新时好时坏"的机制位置）。

### 5.2 与服务器判定的一致性

同发对照（T110E5 打 T110E5，hash 4bb9ff4bcdc7）：WI 射线命中 **84mm 主装甲 @78°**
→ 等效 403mm → HEAT 340 判 BLOCKED，与服务器 result=1（未穿）一致；本项目 P1→P2
弦判定命中同板（服务器 segment B7 装甲组 = 7 亦同），判未穿——**板级一致**。
入射角与穿/弹类别级的残余差异见 §6.3。

## 六、本项目复现实现（射击复现 3D 视图）与收敛路线

### 6.1 数据链：碰撞盒提取（`extract-game` / game_data）

- 来源 = 游戏 YAML `3d/Tanks/Parameters/*.yaml.dvpl` 的 collision 段；
  段名带模型节点号且**零填充**（T110E5 的游戏文件内唯一炮塔/主炮段名为
  `turret_02:`/`gun_06:`），全量收集 `turret_NN:`/`gun_NN:` 段（头行判定排除
  averageThickness 引用行）；
- 顶级配置经 **models.pb 模块id→节点号映射**挑选（tanks.pb 末位炮塔/主炮模块
  匹配 `TurretModelInfo.model_node`/`GunModelInfo.model_node`，缺失回退末位/首段）；
- 枢轴交叉验证：YAML `points` = −部件枢轴（模型系），与 models.pb
  track_origin+turret_origin 逐位一致 → 碰撞盒帧与查看器枢轴帧同一；
- 覆盖率（728 车）：hull/chassis 100%、turret 98%、gun 95%。

### 6.2 判定管线（viewer world 模式 seg 块）

- **出入点标注**：P1/P2 = hash6 按第三篇 §2.1 公式解码（游戏原生盒 1/255 量化点），
  摆放经**部件网格世界矩阵**（网格局部系 = 枢轴系，实测 origPos=0），由位姿链驱动、
  随滑块炮塔/炮管转角联动；段线 = P1→P2（游戏编码命中线段）；
- **判定射线 `__segRay`** = {origin: P1 − 0.5·dir, dir: P1→P2 解码弦}：
  raycast 与入射角**同源此射线**（服务器编码的位置 + 弹向），世界系，优先于
  弦/相机射线源；初始判定/滑块重跑/换弹重跑全线走它；
- **入射角参数**：`/api/penetrate` 的 view_dir = 该射线方向（世界系，与命中法线
  同坐标系）；命中法线 = 世界系面法线（classifyHit）；
- 弹着点红点 = P1；盒缺失回退网格盒并在调试行标注；
- **单点判据**：out1 == out2 → 单点（游戏语义 = 点射终止，未穿/跳弹的可视信号），
  前端解码含 `same` 分支（样本回放暂未观测到单点分支）。

### 6.3 固有差异界限

- **横向偏移不传递**：hash6 两点在部件盒内的横向位置即服务器编码的全部位置信息，
  与真实弹着间存在量化 + 盒源偏差（0.1~0.4m 级）；
- **板源差异**：本项目求交用 itemDefs 装甲网格，游戏/WI 用 collision_client 模型——
  同一块板的面法线/边界有差，入射角与穿/弹类别级（跳弹 vs 未穿）可能不同
  （shot#5 实测：同板 84mm，本地弦向掠射触发跳弹规则，服务器记未穿）；
- **随机化**：游戏内 ±5% 边际判定，本地模拟显示期望结果。

### 6.4 收敛路线（未实现，按收益排序）

1. **数据源升级**：从 `3d/Tanks/CollisionMeshes/*.scg.dvpl` 提取 4 部件 AABB（替换
   item_defs 轴对齐盒），并按坦克型号建立 {右,高,前}→JSON 轴映射表——预期把 ~1m 级
   中位残差压到分米级（格式已解，第一篇 §九）；
2. **全姿态修正**：现行 yaw-only（探针验证过的离散姿态近似），坡地交战可加
   type10 pitch/roll 完整旋转（参照第三篇 §五 VehicleTransformSystem 的 −Y/−X/−Z 轴序）；
3. **method8 result 改写规则**：受害者死亡/零血时 result 4（跳弹）→2
   （@0x16A9271 实证，第三篇 §2.3）——需受击者命中时刻存活状态上下文，
   combat.rs 血量链可提供；量级小（死亡车辆身上的跳弹表现差异），优先级低；
4. **示踪线**：维持直线弹道（与游戏一致）；如需动画级复现，按 30Hz 固定步长 +
   匀速推进 + 0.35 速度阻尼即可（第三篇 §一）。

## 七、`c=` 分享码与活体状态
